# Design — Automação e aprovação

> **Status:** Final / Aprovado para Implementação
> **Data:** 2026-08-29
> **Sub-projeto:** 4 de 5

## Contexto e roadmap

Hoje, quando a geração de uma `ContentPiece` termina com sucesso, ela sempre para em
`status=pending_approval` (`app/services/content/pipeline.py:162`) — e não existe nenhum caminho,
manual ou automático, que a mova dali. A tabela `content_approval_rules` e os campos
`scheduled_for`/`entitlement_status` já existem desde o sub-projeto 1 ("Fundação"), mas nenhuma
lógica de runtime os lê: só há CRUD de `ApprovalRule` (`app/services/content/approval_rules.py`).

Esta fase fecha o ciclo: **gerar → decidir se precisa de humano → aprovar → publicar**, cobrindo
três capacidades que a descrição do roadmap junta numa fase só:

1. **Calendário proativo de geração** — a campanha gera conteúdo novo sozinha, num ritmo de uma
   piece por dia, até preencher `horizon_days` à frente.
2. **Motor de aprovação** — avalia `ApprovalRule` contra cada piece recém-gerada e decide
   `auto_approve` ou `require_review`, mais um endpoint manual para o caso de revisão humana.
3. **Agendamento de publicação** — dispara a publicação (via o motor da fase 3, inalterado) quando
   `scheduled_for` de uma piece `approved` vence.

Um quarto item, o **gate de `entitlement_status`**, atravessa os itens 1 e 3: um tenant fora de
`active` pausa o autopilot (geração proativa e publicação agendada), mas não afeta chamadas
manuais às APIs das fases 2/3, que continuam liberadas como hoje.

Depende dos sub-projetos 2 (motor de geração, `main`) e 3 (motor de publicação, `main`, commit
`c785c14`) — não os modifica, só os chama.

## Princípios arquiteturais

- **Um poller novo, separado do da fase 3** — `app/services/content/automation_scheduler.py` roda
  seu próprio loop no lifespan, com seu próprio intervalo. Não toca em
  `publish_dispatcher.py` (o arquivo mais denso e mais historicamente frágil do módulo) — só chama
  `resolve_publication_request`, uma função pública já existente e já testada.
- **Cadência diária, não tempo real** — ao contrário do dispatcher de publicação (tick de
  segundos, para não segurar um post pronto), este motor decide "que dia postar o quê" — um tick
  de minutos é suficiente e mais barato.
- **Reuso, não reimplementação** — geração de conteúdo (fase 2) e execução de publicação (fase 3)
  continuam com todo o código que já têm. Este motor só decide *quando* e *com quais parâmetros*
  chamá-las.
- **Simplicidade sobre concorrência pesada** — nenhum dos três passes usa
  `SELECT ... FOR UPDATE SKIP LOCKED`. Cada um tem um motivo próprio para dispensar isso (ver seção
  "Concorrência multi-réplica" e o Passe 2 abaixo) — a alternativa mais simples é sempre preferida
  quando o risco residual é coberto de outra forma.
- **Fail-safe sobre otimista** — nenhuma regra configurada, ou regra ambígua, sempre resolve para
  `require_review`. Auto-aprovação é opt-in explícito via `ApprovalRule`, nunca o caminho padrão.

## Modelo de dados

### Tabela nova — `content_generation_templates`

O molde que uma campanha gira automaticamente para gerar conteúdo novo:

```text
content_generation_templates
  id, campaign_id, type (video|image|audio), generation_prompt,
  avatar_id (nullable), voice_id (nullable), is_synthetic_media,
  content_category (nullable), aspect_ratio, resolution (nullable),
  duration (nullable), created_at
```

Uma campanha pode ter vários templates (rotação round-robin — ver Passe 1). Uma campanha sem
nenhum template simplesmente não participa da geração proativa (continua aceitando criação manual
de pieces via API normalmente).

### Campos novos em `content_pieces`

- **`approval_action`** (enum `ApprovalAction`, nullable — reusa o enum já existente
  `auto_approve`/`require_review`) — grava o resultado da avaliação de regra. `NULL` até o Passe 2
  rodar. É o campo que distingue "ainda não avaliada" de "avaliada, aguardando humano" — as duas
  situações têm `status=pending_approval` idêntico; sem este campo o Passe 2 reavaliaria a mesma
  piece a cada tick, indefinidamente.
- **`approved_at`** (datetime, nullable) — espelha `posted_at`. Preenchido tanto por auto-aprovação
  (Passe 2) quanto pelo endpoint manual de aprovação.
- **`is_autogenerated`** (boolean, default `false`) — marca pieces criadas pelo Passe 1. Usado para
  contar a rotação de template (só pieces autogeradas contam) sem confundir com criação manual.

Migração Alembic única cobrindo a tabela nova e os três campos.

## Arquitetura — `automation_scheduler.py`

Loop registrado no `application_lifespan` (mesmo padrão de `start_dispatcher`/`stop_dispatcher` da
fase 3), com tick a cada `CONTENT_AUTOMATION_TICK_SECONDS` (default `300`). Cada tick roda os três
passes abaixo, em sequência.

### Passe 1 — Geração proativa (preenche o calendário)

Para cada `Campaign` com `status=active`, cujo tenant (via `Client.tenant_id`) tem
`entitlement_status=active`, e que tem pelo menos um `content_generation_templates`:

1. Calcula `max_scheduled` = maior `scheduled_for` entre as pieces da campanha com `status` fora
   de `(rejected, failed)`. Pieces `failed`/`rejected` não contam — uma falha de geração não deixa
   um buraco permanente no calendário, o próximo tick tenta de novo por aquele slot.
2. Se não houver nenhuma piece elegível, o próximo slot é `agora`. Senão, é `max_scheduled + 1
   dia`.
3. Se esse slot for menor que `agora + horizon_days`, cria **uma** piece nesse tick (não o
   horizonte inteiro de uma vez — uma campanha nova com `horizon_days=7` leva até 7 ticks
   [~35 min no default] para o calendário ficar cheio; é um comportamento de infraestrutura
   correto, mas **a fase 5 [UI] não deve prometer ao usuário um calendário populado instantaneamente
   ao ativar uma campanha** — nota para o design daquela fase).
4. Escolhe o template pela rotação: `(contagem de ContentPiece.is_autogenerated=true já criadas
   nesta campanha) % (número de templates da campanha)` — o CRUD de templates é só
   create/list (sem soft-delete nesta fase), então "templates da campanha" é sempre a lista
   inteira, sem conceito de ativo/inativo.
5. Chama o `create_piece` + disparo de geração já existentes da fase 2, com
   `idempotency_key=f"auto:{campaign_id}:{slot_date}"` (granularidade de dia — reflete a decisão
   de 1 piece/dia deste design; suportar múltiplos posts por dia exigiria um sufixo de sequência
   na chave, ex. `:{slot_index}`, e não faz parte desta fase). A `UniqueConstraint` já existente em
   `content_pieces (campaign_id, idempotency_key)` funciona como trava de corrida passiva — nenhum
   `SKIP LOCKED` necessário aqui.
6. Piece nasce com `scheduled_for=slot`, `is_autogenerated=true`.

### Passe 2 — Avaliação de regra de aprovação

`SELECT ContentPiece WHERE status=pending_approval AND approval_action IS NULL LIMIT <batch>` —
sem lock: avaliar a mesma piece duas vezes numa corrida rara é inofensivo (determinístico, sem
efeito colateral externo).

Para cada piece:

1. Se `requires_human_review=true` (já calculado na criação pela fase 2, ver `policy.py`) →
   `approval_action=require_review`. É um piso de segurança: nenhuma `ApprovalRule` pode
   auto-aprovar por cima de uma piece que a fase 2 já marcou como alto risco.
2. Senão, percorre as `ApprovalRule` da campanha em ordem de `priority` desc (já implementado em
   `list_approval_rules`). `condition` é um dict onde cada chave presente (`content_category`,
   `risk_level`) lista os valores aceitos; a piece casa com a regra se, para toda chave presente em
   `condition`, o valor correspondente da piece está na lista. `condition={}` casa com qualquer
   piece (regra catch-all, útil como fallback de prioridade baixa). Primeira regra que casa vence.
3. Nenhuma regra casa → `approval_action=require_review` (fail-safe, mesmo default de quando não
   há nenhuma regra configurada).
4. Escreve o resultado com **guarda otimista**: `UPDATE content_pieces SET approval_action=:action,
   status=:new_status, approved_at=:approved_at WHERE id=:id AND status='pending_approval'`. Se
   `auto_approve`: `new_status=approved`, `approved_at=now`. Se `require_review`:
   `new_status=pending_approval` (inalterado, só grava `approval_action`).
5. Se a `UPDATE` afetar 0 linhas, alguém já mudou o status desta piece entre a leitura e a escrita
   (ex.: um humano rejeitou manualmente no meio da avaliação) — descarta a decisão do motor sem
   sobrescrever, loga em nível DEBUG/INFO (é concorrência normal, não um erro).
6. Grava em `content_audit_logs` (`actor="system:approval_engine"`).

A mesma guarda otimista (`WHERE status='pending_approval'`) se aplica aos endpoints manuais de
aprovar/rejeitar (ver "Fluxo de API") — os dois lados (motor automático e humano) escrevem contra
o mesmo predicado, então quem chegar primeiro vence e o outro descarta sem corromper nada.

### Passe 3 — Disparo da publicação agendada

```sql
SELECT * FROM content_pieces
WHERE status = 'approved'
  AND scheduled_for <= now()
  AND NOT EXISTS (
    SELECT 1 FROM content_social_publications
    WHERE content_social_publications.content_piece_id = content_pieces.id
  )
LIMIT :batch_size
```

O `NOT EXISTS` é a fronteira entre este motor (S4) e o executor da fase 3 (S3): garante que o
disparo acontece **uma vez só** por piece — depois que a primeira linha de
`content_social_publications` existe, a fase 3 assume o ciclo de vida inteiro (retry, sucesso,
falha) sozinha; o Passe 3 nunca mais toca nessa piece.

Para cada piece elegível, com o tenant em `entitlement_status=active`: resolve as contas-alvo como
**todas** as `ContentSocialAccount status=active` do client dono da campanha, e chama
`resolve_publication_request` (função já existente de `app/services/content/publications.py`,
inalterada) com essa lista. Nenhum código novo de execução — só a decisão de quando chamar uma
função que já existe.

## Concorrência multi-réplica

Nenhum dos três passes usa `SKIP LOCKED`, então em produção com múltiplas réplicas da aplicação
rodando o mesmo tick simultaneamente, colisões batem direto nas constraints únicas do banco:

- **Passe 1**: duas réplicas tentam criar a piece para o mesmo `campaign_id` + `slot_date` — a
  segunda toma `IntegrityError` na `UniqueConstraint(campaign_id, idempotency_key)`.
- **Passe 3**: duas réplicas chamam `resolve_publication_request` para o mesmo par piece/conta —
  a segunda toma `IntegrityError` na `UniqueConstraint(content_piece_id, social_account_id)` de
  `content_social_publications`.

**Requisito de implementação:** os loops do Passe 1 e do Passe 3 devem envolver o `commit()` de
cada item (cada campanha no Passe 1, cada piece no Passe 3) num `try/except IntegrityError`
individual — nunca um único `try` em volta do batch inteiro, ou uma colisão early derruba o
progresso dos itens seguintes. No `except`: `session.rollback()` (só daquela transação/item),
log em nível INFO/DEBUG (é concorrência normal entre réplicas, não uma falha), e o loop continua
para o próximo item. Isso torna o motor seguro para múltiplas réplicas sem precisar de
`SKIP LOCKED` em lugar nenhum dos dois passes.

O Passe 2 não precisa desse tratamento — sua guarda otimista (`WHERE status='pending_approval'`)
já resolve o caso de corrida por construção, sem depender de uma constraint de banco.

## Fluxo de API

- **`POST /v1/content/pieces/{id}/approve`** — age só se `status=pending_approval` (guarda
  otimista); `status=approved`, `approved_at=now`. `409` se a piece não estiver mais em
  `pending_approval` no momento da escrita.
- **`POST /v1/content/pieces/{id}/reject`** — mesma guarda; `status=rejected`. `409` no mesmo
  caso.
- **`POST /v1/content/campaigns/{id}/templates`** / **`GET /v1/content/campaigns/{id}/templates`**
  — CRUD de `ContentGenerationTemplate`, no mesmo padrão do CRUD de `ApprovalRule` já existente em
  `app/services/content/approval_rules.py` / `app/controllers/v1/content/approval_rules.py`.

## Auditoria

Toda transição de status grava em `content_audit_logs`, seguindo o padrão já estabelecido no
módulo:

- Auto-aprovação e `require_review` do Passe 2 → `actor="system:approval_engine"`.
- Criação automática de piece pelo Passe 1 → `actor="system:automation_scheduler"`.
- Aprovação/rejeição manual → `actor=<owner_user_id do tenant autenticado>`, mesmo padrão dos
  outros controllers.

## Tratamento de erro

Nenhum dos três passes implementa retry/backoff próprio — cada um delega para infraestrutura que
já existe:

- **Passe 1**: uma falha de geração já vira `status=failed` pela fase 2. Pieces `failed` não
  contam para `max_scheduled` (ver Passe 1, passo 1), então o próximo tick tenta de novo o mesmo
  slot com uma `idempotency_key` nova (data seguinte) — autocorretivo, sem lógica extra.
- **Passe 2**: sem chamada externa, sem falha a tratar além da guarda otimista já descrita.
- **Passe 3**: qualquer falha de publicação (rate limit, credencial inválida, etc.) é
  responsabilidade inteira do dispatcher da fase 3, que já tem taxonomia de erro, backoff
  persistido e retry — o Passe 3 só entrega o "start" e sai de cena.
- **Entitlement caindo no meio do caminho**: os passes checam `entitlement_status` a cada tick; se
  cair para `inactive`/`trial`, simplesmente param de agir a partir do próximo tick — nada que já
  esteja em andamento (uma geração rodando, uma publicação já enfileirada) é cancelado.

## Escopo P0 (Entregáveis)

- Migração Alembic: tabela `content_generation_templates` + campos `approval_action`,
  `approved_at`, `is_autogenerated` em `content_pieces`.
- `automation_scheduler.py` com os 3 passes + lifecycle (`start_scheduler`/`stop_scheduler` no
  `application_lifespan`, mesmo padrão de `publish_dispatcher.py`).
- Tratamento de `IntegrityError` por item nos Passes 1 e 3 (seção "Concorrência multi-réplica").
- Guarda otimista (`UPDATE ... WHERE status='pending_approval'`) no Passe 2 e nos endpoints
  manuais de aprovar/rejeitar.
- Função pura de matching de `condition` contra uma piece (testável isolada, sem I/O).
- Função pura de cálculo do próximo slot de calendário e da rotação de template (testável
  isolada).
- Endpoints `POST /pieces/{id}/approve`, `POST /pieces/{id}/reject`.
- CRUD de `content_generation_templates` (create/list) + controller.
- Escrita em `content_audit_logs` em toda transição de status coberta por esta fase.
- `config.example.toml` documentando `CONTENT_AUTOMATION_TICK_SECONDS`.

## Não-objetivos (ficam para specs futuras)

- Limites quantitativos de custo/geração (N gerações/mês por plano) — `entitlement_status` nesta
  fase é só um gate binário ativo/inativo; não existe hoje nenhuma infraestrutura de contagem de
  uso no código, e construí-la é escopo próprio caso vire necessidade real.
- Múltiplos posts por dia por campanha — o design do Passe 1 é 1 piece/dia; suportar mais exigiria
  estender a chave de idempotência com um índice de slot.
- Uma lista de contas-alvo configurável por campanha para a publicação agendada — o Passe 3 sempre
  usa todas as contas ativas do client. Um subconjunto configurável é extensão futura se a
  necessidade aparecer.
- Qualquer UI (telas de aprovação, configuração de templates/regras, calendário visual) — fase 5.
- Qualquer alteração em `publish_dispatcher.py` ou nos adapters da fase 3 — este design só os
  chama, nunca os modifica.
